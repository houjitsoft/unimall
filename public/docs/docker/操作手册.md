# Docker 部署操作手册（模式 A 全栈 / 模式 B 外部中间件）

> 适用对象：要在**新机器从零起环境**的人（模式 A），以及**机器上已经有 Nacos / MySQL / Redis、
> 只想把业务服务迁进容器**的人（模式 B）。
>
> 一句话：默认只看 `docker-compose.yml` 一份；模式 B 再叠 `docker-compose.hostnet.yml`。
> 首次部署建议直接跑 `bash deploy/install.sh`（自动生成口令、起中间件、建库导配置、起服务、验收），
> 本手册解释它做了什么、以及手工编排时怎么避坑。

| | 模式 A：全栈一键 | 模式 B：外部中间件 / host 网络 |
|---|---|---|
| 适用场景 | 首次部署、新机器、演示、CI | 宿主机已跑着 Nacos / MySQL / Redis |
| 编排命令 | `docker compose up -d`（或 `bash deploy/scripts/docker.sh up`） | `docker compose -f docker-compose.yml -f docker-compose.hostnet.yml up -d --no-deps <svc>` |
| 容器网络 | bridge（compose default 网络） | host（容器直接用宿主机网络栈） |
| 中间件在容器里吗 | 在（MySQL / Redis / Nacos / RocketMQ 全部由 compose 起） | 不在，用宿主机上已有实例 |
| Nacos 地址默认值 | `nacos:8848`（服务名） | `127.0.0.1:8848`（可用 `NACOS_ADDR` 覆盖） |
| 自动初始化 | MySQL 首启建库建表 + `nacos-init` 导入 39 个配置 | 无（配置应在外部 Nacos 里已经就位） |

两种模式**不要同时在同一台机跑**：中间件会被两套编排争端口（典型症状是 8848 / 3306 的
`Bind for 0.0.0.0:xxxx failed: port is already allocated`）。

## 0. 部署资产都在 `deploy/` 目录（合并后的单一入口）

部署相关的一切集中在仓库的 `deploy/` 目录（编排 YAML 除外——按 compose 生态惯例留在仓库根，
`docker compose up` 不用带 `-f`）：

| 位置 | 内容 |
|---|---|
| `deploy/install.sh` | 一键装机入口（推荐首次使用） |
| `deploy/verify-plugin-chain.sh` | 插件全链路 12 步自动验收 |
| `deploy/Dockerfile.*` | 4 份镜像定义：builder（编译）/ service（Java 服务）/ frontend（后台）/ nacos-init |
| `deploy/build-jars.sh` | jar 编译编排（含架构门禁） |
| `deploy/mysql-init/` | MySQL 首启建库建表（`00-init.sql`，勿手改，由 render 生成） |
| `deploy/nacos-init/` | Nacos 首启初始化（模板渲染 + 39 dataId 导入） |
| `deploy/scripts/sql/` | SQL 种子源（改顺序改 `order.txt`，再跑 render） |
| `deploy/scripts/nacos-templates/` | Nacos 配置模板与渲染变量样例 |
| `deploy/scripts/architecture/` | 架构门禁（`services.json` 校验，构建期强制） |
| `deploy/scripts/docker.sh` | compose 双轨入口（up / demo / full / mw / build / reset …） |
| `deploy/rocketmq/`、`deploy/nginx/` | broker 双轨配置 / 后台 Nginx 配置 |

> 历史：曾经存在 `docker/` 与 `deploy/` 两个目录（材料与动作分离），2026-10 起合并为
> `deploy/` 单一入口。旧文档里的 `docker/scripts/...` 一律对应现在的 `deploy/scripts/...`。

## 1. 编排文件清单（谁管什么，别选错）

| 文件 | 用途 | 什么时候用 |
|---|---|---|
| `docker-compose.yml` | **唯一权威编排**：中间件 + 核心服务 + builder + `ai`/`commerce`/`es` 三个 profile | 模式 A、install.sh、docker.sh 全走它 |
| `docker-compose.hostnet.yml` | 模式 B 叠加 patch（只改 `network_mode: host` 和 Nacos 地址，不重复定义） | 中间件在宿主机时，与主文件**叠加**使用 |
| `docker-compose.middleware.yml` | 只起中间件的独立网络形态（MySQL / Redis / Nacos / RocketMQ，项目名 `${COMPOSE_PROJECT_NAME:-unimall}-mw`），broker 用 `broker-host.conf` | 服务 jar 跑在宿主机、只要容器化中间件的形态 |
| `docker-compose.commercial.yml` | 商业服务**制品镜像版**（`UNIMALL_*_IMAGE` 指向外部镜像，无 build 段） | 购买了商业服务制品镜像的客户；与 `--profile commerce` 二选一 |

### 1.1 开源包的可用边界（重要）

开源仓库只包含 **12 个后端模块**（`backend/paas/`：auth / base / commons / goods / job / merchant /
order / payment / permission / thirdparty / tool / userms + `backend/bff/bff-web`）。
`docker-compose.yml` 为了保持与商业版同一份编排，仍声明了全部服务，因此——

- **默认启动集可用**：permission / auth / userms / base / bff-web（`install.sh` 起的就是这 5 个），
  再加 goods / order / payment / merchant / job / thirdparty 也都有源码可 build。
- **这些服务在开源包里 up 会在 build 阶段失败（预期行为，不是坏了）**：
  - `mall` `supplier` `oa` `geo` `logging`（默认启动但源码未开源）；
  - `--profile ai` 下的 `aicode`、`--profile commerce` 下的 10 个商业服务（crm / cms / erp / finance /
    im / mes / orderfood / pm / rider / webpos）——builder 镜像里没有它们的 jar，`compose up` 构建
    镜像时会报找不到。需要这些服务时：向官方购买源码（走 commerce profile 本地构建）或
    制品镜像（叠加 `docker-compose.commercial.yml`），二者**容器名相同，不能同跑**。

### 1.2 Redis 双形态说明

模式 A 里 Redis 是 compose 服务（`unimall-redis`，bridge 网络按服务名 `redis:6379` 互通）。
`.env` 的 `REDIS_ADDR` 默认值即 `redis:6379`；模式 B 改成 `127.0.0.1:6379`（或真实地址），
`nacos-init` 会把它渲染进 Nacos 的 `redis.yaml` 下发给全部服务。

## 2. 模式 A：全栈一键（默认）

### 2.1 前置

- Docker 24+（含 Compose v2）；内存：核心 5 服务 ≥ 8GB，全量业务 ≥ 28GB
- 仓库根目录下准备好 `.env`（`cp .env.docker.example .env`，或直接跑 install.sh 自动生成）

### 2.2 三条入口，按需选

```bash
# 入口〇：界面化安装向导（推荐新用户）——起 install profile 两个安装期容器，
#         浏览器点选完成安装，详见 2.2.1
bash deploy/install.sh --wizard

# 入口一：一键装机（命令行）——校验环境、随机口令、起中间件、建库、
#         导 Nacos 配置、起 5 个核心服务、接口验收，一步到位
bash deploy/install.sh            # 加 --with-admin 再起管理后台前端

# 入口二：手工 compose —— 已有 .env、想精确控制起哪些服务
bash deploy/scripts/docker.sh up         # = build builder 镜像 + compose up -d --build
bash deploy/scripts/docker.sh ps         # 容器状态一览
bash deploy/scripts/docker.sh logs <svc> # 跟某个服务的日志
bash deploy/scripts/docker.sh down       # 停全部（保留数据卷）
bash deploy/scripts/docker.sh reset     # ⚠ 连数据卷一起删，库会重新初始化
```

首次会编译后端（约 10~20 分钟）。启动过程中两个一次性任务自动完成，无需人工干预：

1. **数据库初始化**：MySQL 容器首启执行 `deploy/mysql-init/00-init.sql`，`source` 进
   `deploy/scripts/sql/init/` → 建库 + 700 余张表 + 菜单 / 角色 / 初始管理员。
   库名由 `MYSQL_DATABASE` 决定（默认 `meoc`），init SQL 里不再写死 `USE`。
2. **Nacos 配置导入**：`nacos-init` 一次性任务等 Nacos 就绪后渲染变量表，
   导入 39 个 dataId 到 `houeoc` 命名空间。等待逻辑用 `compose ps -aq`（含已退出容器），
   退出码 0 才算成功，不会白等超时。

### 2.2.1 界面化安装向导（`install.sh --wizard`）

向导 = 命令行安装内核（install.sh）+ 界面层，产物与命令行完全一致（同一份编排、同一套种子、
同一套口令随机化）。组成：

| 组件 | 位置 | 作用 |
|---|---|---|
| 向导页面 | `public/install/`（nginx 静态托管，零构建原生 JS） | 5 步向导：环境检测 → 模式选择 → 配置确认 → 安装进度 → 完成 |
| install-web | compose `install` profile | 安装期 nginx：根路径 302 进 `/install/`；`/install/api/` 反代 agent |
| install-agent | `deploy/install-agent/app.py`（纯标准库 Python） | 安装编排 API：环境检测、连通测试、逐阶段调 `install.sh --stage`、进度流、重试/重置/收尾 |

**流程**：`--wizard` 起 install profile → 浏览器访问 `http://<IP>:$WEB_PORT/` 自动跳转安装页 →
选模式 → 安装 → 完成页点「启动管理后台」→ agent 停 install-web、起 admin-web 接管端口 →
之后访问域名即管理后台（向导自然消失，无需运行时判断）。

**两种安装模式**：

- **Docker 默认安装**：自动创建 MySQL / Redis / Nacos / RocketMQ 容器 + 5 个核心服务，
  数据库与 Nacos 配置全自动初始化；完成页展示各服务访问地址（口令留在服务器 `.env`，页面不回显）。
- **自定义安装（外部中间件）**：填写你自己的 MySQL（地址/端口/账号/密码/库名）、Redis、
  Nacos、RocketMQ（选填）连接信息 → 页面逐项「测试连接」 → 通过后以 host 网络部署应用服务，
  直连灌库（`init_all.sh` 逻辑）+ 向你的 Nacos 导入配置。模板中数据库账号与库名已变量化
  （`${MYSQL_USER}` / `${MYSQL_DB}`），可使用任意账号与库名。

**环境检测**（进入向导第一步自动执行）：Docker Engine / compose 可用性（致命）、内存/CPU/磁盘
建议值（警告）、目标端口是否被本项目之外的容器占用（警告）。致命项不过关无法进入下一步。

**安装状态持久化**（防重复进入安装流程）：唯一权威是 `data/install-state.json`
（`state ∈ none | installing | installed | failed` + 当前阶段 + 错误信息 + 完成信息）。三道闸：
1. 已安装后 agent 拒绝一切再次安装请求（HTTP 409）；
2. 向导页加载即查状态，`installed` 直接渲染完成页并锁死重装入口；
3. 安装完成后 install-web 容器即停、端口交还 admin-web，`/install/` 从此只显示「已完成」提示页。

**失败重试与回滚**：安装按阶段（配置 → 中间件 → 构建 → 启动 → 验收）推进，各阶段幂等
（`.env` 不覆盖既有口令、compose up 复用容器、nacos-init 强制重建）。失败时停在出错阶段并
保留完整日志，点「从失败阶段重试」即从该阶段续跑，**无需从头安装**；浏览器/agent 重启后重开
向导会自动恢复到「安装进行中」视图。要彻底重来：向导页输入 `RESET`（停服务保数据）或
`PURGE`（删数据卷，不可恢复）全词确认码。

**安全注意**：安装期间 install-agent 持有 docker.sock 与仓库写权限（install profile 特性，
安装完成即停）。**切勿把 `$WEB_PORT` 暴露到公网**，反代域名仅限受信网络；口令均写入服务器
`.env`（权限 600），不经过浏览器。

**向导与命令行等价性**：`--stage` 是向导 agent 的编排原子（`env / env-custom / infra / build /
apps / smoke / custom-db / nacos-import`），命令行用户也可单独调它做局部重跑；state 文件在
命令行整流程结束时同样落盘，两条路径互通。


### 2.3 builder 镜像的源码指纹（防止「改了代码却跑旧的」）

`install.sh` 构建的服务镜像 tag 带源码指纹（`src-<git short HEAD 或内容哈希>`）：
源码一变，指纹变，镜像必然重建。**不要手工给 builder 镜像固定 `latest` 后反复复用**——
compose 的 build 段在镜像已存在时会跳过构建，jar 烤的是旧代码，日志还全绿，极难察觉。
手工路线的等价做法：每次改完代码先 `docker compose build builder`（或删掉旧 builder 镜像）再 up。

### 2.4 端口避让

`.env` 里每个中间件都有独立宿主端口变量（`MYSQL_HOST_PORT` / `REDIS_HOST_PORT` /
`NACOS_HOST_PORT` / `NACOS_GRPC_PORT` / `NACOS_GRPC_RAFT_PORT` / `ROCKETMQ_*` / `WEB_PORT` /
`BFF_PORT`）。机器上已有 MySQL/Nacos 等时改这些值；`install.sh` 启动前会逐一探测端口并拒绝启动，
按提示改 `.env` 即可。注意 Nacos 2.x 除了 8848 还要通 **9848（gRPC，= 8848+1000）** 与 9849。

### 2.5 NACOS_AUTH_TOKEN 的格式要求

Nacos 2.3.2 的 `nacos.core.auth.plugin.nacos.token`（即 `.env` 的 `NACOS_AUTH_TOKEN`）要求
**base64 编码、且解码后 ≥32 字节**。写成 hex 会启动失败，而报错只提
`basicAuthenticationFilter` 依赖失败，极具迷惑性。生成方式：

```bash
openssl rand -base64 32
```

`install.sh` 生成的值已满足要求，并在启动前校验、不合法会自动重生成。

## 3. 模式 B：外部中间件 / host 网络

### 3.1 前置**（逐条确认，少一条都会起不来）**

1. 宿主机上 Nacos / MySQL / Redis / RocketMQ 已经在跑，且端口能被本机访问。
2. 外部 Nacos 里 `houeoc` 命名空间的 mutual.yaml / redis.yaml / rocketmq.yaml 指向正确的
   MySQL / Redis 地址 —— **业务服务的库连接串是从 Nacos 下发的，不在 compose 里配**。
   外部 MySQL 还是**空库**时，先直连初始化（模式 A 是容器首启自动灌，模式 B 没有这步）：

   ```bash
   export MYSQL_HOST=127.0.0.1 MYSQL_PORT=3306 MYSQL_USER=root MYSQL_PASSWORD=xxx
   export I_ACCEPT_EULA=yes   # 表示已阅读并同意开源 EULA
   bash deploy/scripts/sql/init_all.sh   # 建库 + Core 全量表结构 + 初始数据（不含插件表）
   ```

3. `.env` 里设好 `NACOS_ADDR`（见 3.3）。
4. builder 镜像已构建（各服务镜像只从它 COPY 自己那一个 jar）：

```bash
docker build -f deploy/Dockerfile.builder -t unimall/builder:latest .
```

### 3.2 命令

```bash
# 1) 只打目标服务的镜像（示例：goods + userms）
docker compose -f docker-compose.yml -f docker-compose.hostnet.yml build goods userms

# 2) 起容器：🔴 --no-deps 必须带
docker compose -f docker-compose.yml -f docker-compose.hostnet.yml up -d --no-deps goods userms
```

**`--no-deps` 为什么必须带**：主文件里每个业务服务都 `depends_on: mysql / nacos / ...`，
不带 `--no-deps` 时 compose 会先把这些中间件拉起来，去抢宿主机上已被占用的 8848 / 3306 / 6379，
报 `Bind for 0.0.0.0:8848 failed: port is already allocated`，结果目标服务根本没起来。
（不要为此去改主文件的 `depends_on` —— 那会破坏模式 A 的启动顺序。）

**改旧容器前先认领**：compose 认领不了由 `docker run` 起的同名容器，
直接 up 会报 `The container name "/unimall-xxx" is already in use`（`--force-recreate` 也无效），
先 `docker rm -f unimall-<svc>`。删之前用 `docker inspect` 抄下旧容器的启动参数。

### 3.3 环境变量（写进 `.env`）

| 变量 | 含义 | 模式 B 常用值 |
|---|---|---|
| `NACOS_ADDR` | 注册中心 + 配置中心地址 | 本机 `127.0.0.1:8848`；远端填它的真实地址 |
| `NACOS_NAMESPACE` | 命名空间 | `houeoc`（**不是** `houcloud` / `public`） |
| `NACOS_USER` / `NACOS_PASSWORD` | 连 Nacos 的账号口令 | 与外部 Nacos 的实际口令一致 |
| `XXL_JOB_PASS` / `RESTART_ADMIN_TOKEN` | **bff-web 独有必填**（bootstrap.yml 无默认值占位符） | 任意随机串；不设则 bff-web 启动即崩 |
| `JAVA_OPTS` | JVM 参数 | 默认 `-Xms256m -Xmx900m -Dfile.encoding=UTF-8` |
| `SERVICE_MEM_LIMIT` 等 | 容器内存上限 | 默认 1200m |

**口令优先级：`NACOS_PASSWORD` > `NACOS_AUTH_PASSWORD` > 默认值 `nacos`**。
两个名字都能生效，但模式 A 下别让它们取值不一致：那会让容器里的 Nacos 服务端和
连它的业务服务口令对不上。

⚠ **连远端 Nacos 时别忘了 gRPC**：Nacos 2.x 客户端用 9848 做注册与配置长轮询。
只通 8848 的典型症状是「能拉到配置，但服务注册不上 / 反复 `Server check fail, port 9848`」。

`docker-compose.hostnet.yml` 覆盖的就是上表的 `NACOS_*` 四项，默认 `NACOS_ADDR=127.0.0.1:8848`。
数据源 / Redis **刻意不在 override 里注入**：它们由 Nacos 配置下发，
多传一个空值变量反而可能把配置里的默认值顶掉。

### 3.4 端口（host 网络下就是宿主机端口）

| 端口 | 服务 | 端口 | 服务 |
|---|---|---|---|
| 8391 | bff-web（网关） | 8209 | order |
| 8392 | auth | 8207 | payment |
| 8300 | permission | 8220 | mall（商业版） |
| 8214 | base | 8210 | merchant |
| 8195 | userms | 8194 | thirdparty |
| 8208 | goods | 8313 | job |

host 网络下没有端口映射：容器直接 Listen 宿主机端口，该端口若已被别的进程占用会起不来
（Java 侧报 `BindException: Address already in use`）。bff-web 那条 `ports:` 会被 daemon
忽略并打一条 `Published ports are discarded when using host network mode` WARNING，属预期。

## 4. RocketMQ broker 的两份配置（有意设计，别改混）

| 文件 | `brokerIP1` | 给谁用 |
|---|---|---|
| `deploy/rocketmq/broker.conf` | `rocketmq-broker`（容器名） | 模式 A：**消费端也是容器**，按服务名互通 |
| `deploy/rocketmq/broker-host.conf` | `127.0.0.1` | `docker-compose.middleware.yml`：**消费端 jar 跑在宿主机**，NameServer 会把 brokerIP1 回给宿主机进程，写容器名解析不了 |

用哪个由编排文件的 volumes 决定，不需要手工干预；同时知道**为什么有两份**，
排查 MQ 连不上时先确认「消费端在哪跑、broker 用的哪份 conf、回给它的地址能不能解析」。

## 5. 编排文件校验（改编排必跑，不需要 Docker daemon）

```bash
# 模式 A
docker compose -f docker-compose.yml config >/dev/null

# 模式 B
docker compose -f docker-compose.yml -f docker-compose.hostnet.yml config >/dev/null

# 确认 NACOS_ADDR 取值符合预期
docker compose -f docker-compose.yml config | grep -m1 NACOS_ADDR                              # nacos:8848
docker compose -f docker-compose.yml -f docker-compose.hostnet.yml config | grep -m1 NACOS_ADDR # 127.0.0.1:8848
```

`config` 只需要 `.env` 齐全，不需要 daemon 在跑。

## 6. 怎么判断「真的起来了」（从外到内四层，别只看一层）

1. **容器在不在 / 有没有 crash-loop**：`docker ps`，Status 要能持续累积；
   一直显示 `Up 1 second` 说明反复重启 → 看日志。
2. **日志有没有 Spring Boot 启动完成**：`docker logs --tail 200 unimall-<svc>` 里出现
   `Started XxxApplication in ...`。
3. **端口 LISTEN**：host 模式 `ss -lntp | grep <port>`；bridge 模式在容器内探
   `docker exec unimall-<svc> bash -c ':</dev/tcp/127.0.0.1/<port>'`（compose 的 healthcheck 就是这么探的）。
4. **注册到 Nacos**：控制台 → 命名空间 `houeoc` → 服务列表出现该服务。

补充口径：

- 未登录打网关接口，返回 **HTTP 401 `{"code":401,...}`** 是正常（未登录被鉴权拦下 = 后端活着）。
- 业务服务**没有 actuator**，打 `/actuator/health` 会返回项目自己的
  `{"code":404,"message":"接口还未加载"}` —— 这反而说明它在响应；只有 bff-web 有 actuator。

## 7. 常见故障与解法

### 7.1 `UnknownHostException: nacos`（模式 B）

**原因**：`NACOS_ADDR` 仍是模式 A 的容器内服务名 `nacos:8848`。host 网络下容器不进 compose 网络，
没有 `nacos` 这条 DNS 记录。

**解法**：`.env` 里把 `NACOS_ADDR` 覆盖成真实地址后重建容器，先 `config | grep NACOS_ADDR` 确认插值生效。

### 7.2 `Bind for 0.0.0.0:8848 failed: port is already allocated`

**原因**：`up` 没有带 `--no-deps`，compose 去拉 `nacos`（以及 mysql / redis / rocketmq），
而宿主机已有实例占着这些端口。

**解法**：补 `--no-deps`；已经误起了中间件容器的，先 `docker compose stop` 再 `docker rm` 掉它们，
**不要删数据卷**。

### 7.3 `service xxx declares mutually exclusive network_mode and networks`

**原因**：compose 规范里 `network_mode` 与 `networks` 互斥。主文件为此**不声明任何 `networks`**，
服务自然落进 default 网络（模式 A 按服务名互通的能力不变，同时解锁模式 B 叠加 host）。
自己 fork 的版本若加回了 `networks:`，会直接破坏模式 B。

### 7.4 `Could not resolve placeholder 'XXL_JOB_PASS'`

只有 bff-web 会报：它的 bootstrap.yml 里 `xxl.job.admin.password` / `restart.admin.token`
是无默认值占位符（其余服务不需要）。在 `.env` 里补这两个变量即可；编排层用的是
`${XXL_JOB_PASS:?…}` 硬必填语法，缺了会直接拒绝渲染。

### 7.5 报 `缺少必要的spring.redis.*配置`（伪装成「配置缺失」的 Nacos 鉴权失败）🔴 高迷惑性

**现象**：

```
IllegalStateException: 缺少必要的spring.redis.*配置（host/port/database），
请检查Nacos的redis.yaml是否正确加载
```

第一反应会以为是 `redis.yaml` 没导入 / 数据源没配 —— **几乎 always 不是**。

**真因**：Nacos **鉴权失败**（口令或命名空间不对）。此时 Nacos **是连得上的**
（日志里照样有 nacos 客户端的启动、销毁记录，看起来「一切正常」），
但拉取配置被拒，于是所有依赖 Nacos 配置的属性都为空，最后在最早读到的那个 Bean 上炸出来 ——
谁先加载谁背锅，所以报错点看起来跟 Nacos 毫无关系。

**排查（第一条就是判据）**：

```bash
# 1) 看渲染出来的口令是不是你以为的那个值（都没写时会渲染成 nacos —— 那就是没吃到）
docker compose -f docker-compose.yml -f docker-compose.hostnet.yml config | grep NACOS_PASSWORD
# 2) 顺手确认命名空间（必须是 houeoc）
docker compose -f docker-compose.yml -f docker-compose.hostnet.yml config | grep NACOS_NAMESPACE
# 3) 用容器里的值去真连一次
curl -s "http://<NACOS_ADDR>/nacos/v1/cs/configs?tenant=houeoc&dataId=redis.yaml&group=DEFAULT_GROUP&username=nacos&password=<渲染出来的口令>"
```

### 7.6 nacos-init 等待超时 / 白等

`nacos-init` 是一次性任务（exited 即完成）。判断它成功不要用 `compose ps -q`
（只列**运行中**容器，任务退出后拿不到 ID），用 `compose ps -aq` 拿到容器后看
`ExitCode=0` 才算成功。`install.sh` 已按此实现；手工排查时同理。

### 7.7 改了代码但行为没变

九成是**复用了旧 builder 镜像**（见 2.3 指纹说明）：compose 的 build 段在镜像存在时跳过构建，
jar 烤的还是旧代码。先 `docker images` 看 builder 与目标服务镜像的创建时间，
必要时 `docker compose build --no-cache builder <svc>`。

## 8. 同机跑第二套（预发 / 验收 / 演示）

改 `.env` 两处即可与已有那套共存：

```bash
COMPOSE_PROJECT_NAME=unioss        # 容器名/卷名前缀（默认 unimall）
IMAGE_TAG=oss                       # 镜像 tag（默认 latest）——两套不改这个会互相覆盖镜像
```

再把全部 `*_HOST_PORT` / `BFF_PORT` / `WEB_PORT` 挪到空闲端口。两套的容器名、数据卷、
镜像名都由这两个变量隔离，互不可见。
